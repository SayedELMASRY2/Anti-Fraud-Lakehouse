⚖ ARCHITECTURAL TRADE-OFFS • DESIGN RATIONALE

ARCHITECTURE TRADE-OFFS & TECHNOLOGY SELECTIONS

Deliberate engineering decisions made between conflicting technical paths to maximize throughput, data integrity, and operational simplicity.

KAFKA / MSK VS RABBITMQ ⚖
SELECTED: AMAZON MSK (KAFKA)
Rationale: Partitioned log architecture (key=user_id) guarantees per-cardholder sequential ordering and unlimited replayability for downstream backfills, which traditional message queues cannot support.
REDIS ELASTICACHE VS RDBMS FOR STATE ⚖
SELECTED: REDIS SORTED SETS (ZSET)
Rationale: Calculating sliding window counts in PostgreSQL requires expensive range scans under write locks. Redis ZSET provides O(log N + M) rolling window evaluation in 1.11ms without disk I/O.
LIGHTGBM VS DEEP LEARNING (TRANSFORMERS) ⚖
SELECTED: LIGHTGBM v2 C++ CORE
Rationale: Deep Learning models introduce 50–200ms GPU inference latency and lack native split explainability. LightGBM evaluates 34 numerical features in 0.5ms on commodity CPU with full feature attribution.
ZERO-DB STREAMING VS IMMEDIATE DB WRITES ⚖
SELECTED: ZERO-DB DIRECT STREAMING
Rationale: Eliminates relational write lock contention at 100+ TPS. Relational storage is reserved strictly for demographic entities (users & cards) captured via Debezium CDC.
